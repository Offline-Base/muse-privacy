# Contracts

Every module codes against this file. Shared dataclasses are in `base/types.py`, settings in `base/config.py`. If you need a contract change, make it here and in the code together, and say so in your report. This file describes the code as of Oct 27, after integration and the review fixes (see the last section). What these interfaces defend against, and what is still open, is in docs/THREAT_MODEL.md.

## Data flow

```
Muse (cloud VM) --MCP over HTTPS--> relay (Cloudflare Worker) <--WebSocket dialed out by device-- base/connector/relay_client.py
                                                                                       |
                                                                         base/connector/server.py (127.0.0.1:8790)
                                                                                       |
     tool call -> restore tags in arguments -> workspace / jobs -> raw local result (real names, stays here)
                                                                                       |
            guard.tag(raw, llm_names=Glimmer's second pass) -> TagResult
            + request topics (never-share keywords in Muse's request, Glimmer's request_topics pass) -> router.decide() -> RouteDecision
                                                                                       |
               share_tagged: tagged text | share_summary: local summary, tagged | ask_user: approval row, wait | refuse: held message
                                                                                       |
                                         egress.final_check(text) (leak check, last line of defense) -> Muse
```

`base/egress.py` is the single exit. Every connector tool result goes through `egress.release(...)` or `egress.resolve(...)`, which run the router outcome and a final leak check against the roster, the persistent tag map and `guard.find_identifiers`. If the final check finds anything, the result is replaced with "Held on your device." and an audit row records `egress_blocked`. No other code path returns document-derived text to Muse.

All but the last two are in `.env.example`. On a Jetson the model service reads its model from the last `GLIMMER_GGUF=` line of `/etc/muse-privacy/env` (`deploy/jetson/install.sh --model-file FILE --model-sha256 HEX` copies a GGUF from a USB stick, checks it and writes that line), else the i1-IQ1_S file: `glimmer-env.sh` (ExecStartPre) writes `GLIMMER_GGUF` and `LORA_ARGS` to `/var/lib/muse-privacy/glimmer.env`, refuses a missing or relative model path, and the unit runs `--model ${GLIMMER_GGUF}`.

`assert_synthetic(settings, folder)` raises `CloudBackendRefused` when the backend is a cloud endpoint and neither the folder nor a parent of it up to and including `settings.workspace_root` has a `.synthetic` file (`synthetic_marked(folder, root)`). A marker above the workspace root never counts, and a folder outside the root is refused. The index, the agent and egress call it before any document text can reach a cloud model.

Synthetic manifest (`base/manifest.py`, GAP-19): beside each marker sits `.synthetic-manifest.json`, `{"version": 1, "note", "files": {POSIX path relative to the marker's folder: sha256}}`. `synthetic_folder(folder, root) -> Path | None` finds the nearest marker as above, and `synthetic_marked` is True only when that folder's manifest reads and every file under it, at any depth, is listed with a matching hash (`manifest.check(folder) -> Check(found, unlisted)`). Only `.synthetic`, the manifest and `.DS_Store` are left out; other hidden files count, a link counts as its target (which must be listed inside the folder), and a listed file that is gone does not matter. So on a cloud backend `assert_synthetic` also refuses a marked folder that holds a stray or changed file, with one sentence that gives the count of such files and never a name, and the agent's and egress's `synthetic` flags are False for it, so no remote client (Jetson gateway, cloud heavy worker) gets its text. On a local backend nothing reads the manifest. `scripts/make_manifest.py [FOLDER ...] [--check]` writes it from `git ls-files` (tracked regular files, no links), so an untracked or excluded file is never listed; `demo/`, `eval/sam_pages/` and `tests/fixtures/workspace/` have committed manifests, kept current by a test (every tracked `.synthetic` folder; `scripts/make_manifest.py --check`). Tests mark a temp folder with `tests/synthetic_helpers.mark_synthetic(folder)` after writing its files. A cloud eval or red-team script that reads a folder calls `assert_synthetic` or `synthetic_marked`, as `scripts/cloud/quant_eval_modal.py --check` does.

`DEVICE_ONLY=1` (Settings.device_only): every model is on this device, and `guard.Redaction.name_shapes` tags capitalized words shaped like a name as `[Person N]` with no model, unless a folder sends real names or a never-redact word covers them. `PRIMARY_MODEL` defaults to lfm, and LFM3-VL-2B on the checker's llama-server answers every step, the router included, whatever `GLIMMER_BACKEND` says. `PRIMARY_MODEL=glimmer` is allowed only with `GLIMMER_BACKEND=llama_server` on loopback addresses. The Jetson gateway settings and the Meta API key are dropped, so no remote client can be built. When the model is down there is no fallback: the checks fail and results are held.

## Types (`base/types.py`)

- `Person(name, first, last, nicknames=(), role="student", student_id=None)`; `Roster(teacher, students: tuple[Person, ...], school=None)`; `Roster.people()` yields teacher then students. Frozen; `load_roster` returns tuples.
- `Hit(kind, value, start, end)`, kind one of `student, teacher, person, phone, email, ssn, card, otp, student_id, address, dob` (`IDENTIFIER_KINDS` is the last eight). Egress may also report `check_failed`.
- `TagResult(text, tag_map, hits, blocked, topics)`: `tag_map` maps each tag used in this text (like `[Student C]`) to its real value; `blocked` holds plain reasons, `topics` the never-share topic names.
- `Decision` is `share_tagged | share_summary | ask_user | refuse`; `STRICTNESS`, `stricter(a, b)`, `default_share_form(kind, topics=())` (`share_summary` for `class_aggregate` or when `CLASS_LEVEL_TOPIC` (`"class_level"`, a request topic) is in `topics`, else `share_tagged`).
- `RouteInput(request, result_kind, tagged_text, hits=[], blocked=[], summary=None, topics=[], request_blocked=[])`: `hits` are the result's plus the identifier hits in Muse's request; `request_blocked` lists the never-share topics named only in Muse's request, not in the result (they stay in `topics` too). `RouteDecision(decision, reason, source, latency_ms=0, floors=[], code="", calls=0, prompt_tokens=None, completion_tokens=None, reasoning_tokens=None, finish_reason=None)`, source `model | rule | fallback | cache`; `code` is a fixed string for what decided it (Router lists them), never model text, empty when unknown. The usage fields are the router model's for this decision (`calls`: completions sent, retries included; 0 on a path with no model call; the token counts are None when the server reported none). Egress builds new RouteDecisions for its holds without them, so the eval reads them from the router's own decision (`RouterTap.last_decision`).
- Result kinds: `document_list, snippet, per_student, class_aggregate, contact_info, sensitive_record, free_text, dreaming_report`.

## Guard (`base/guard.py`)

- `load_roster(path) -> Roster`. `GuardError` for an unreadable tag map or text that still has private values after tagging.
- `find_identifiers(text, roster=None, *, allow_test_ssn=True) -> list[Hit]`: Luhn-valid 13 to 19 digit cards, SSNs (000 and 9xx areas accepted unless `allow_test_ssn=False`), US phone formats, emails, one-time codes next to code/OTP/PIN/verification, student ids (`S` or `ID` plus 5 to 8 digits, and the roster's id shape when a roster is given), numbered street addresses, dates of birth next to born/DOB/birthday. Plain calendar dates are not identifiers.
- `find_names(text, roster)`: full names, first names, capitalized last names, nicknames, possessives, a teacher's title plus last name, one-edit misspellings of capitalized 4+ letter tokens that are not common words. A first name two students share becomes `[Person N]`; relatives with a roster surname too (up to two capitalized words before it, accented ones included: Émile Tindall). A student's dotted initials ("C.R.", "C. R.") count within 60 characters of a class word (`_CLASS_CONTEXT`), unless they are an ordinary abbreviation (`_NOT_INITIALS`: T.V., H.W., A.M.), part of a longer run (G.P.A.) or come before a name ("C.R. Fenwick"); initials two students share become `[Person N]`.
- `TagMap(path=None, *, seed=None, rotation="off", grace_hours=36, clock=None, backup=())`, `TagMap.load(path)`, `TagMap.for_settings(settings)` (rotation and grace from `TAG_ROTATION` and `TAG_GRACE_HOURS`, and `backup=[paths.db]`): persistent at `settings.paths.tagmap`, written 0600 atomically. Students get `[Student A]`... in a per-device shuffled order, the teacher `[Teacher]`, others `[Phone 1]`, `[Email 1]`, `[SSN 1]`, `[Card 1]`, `[Code 1]`, `[ID 1]`, `[Address 1]`, `[DOB 1]`, `[Person 1]`. Codes only go up (`next_letter`, per-kind counters), so a code never names two values; past `[Student ZZZ]` (18,278 codes, `MAX_STUDENT_CODES`) `tag_for` raises `GuardError`. `clock` (default `time.time`, a public attribute) gives the time.
  - Version 2 file: `{version: 2, seed, rotation, next_letter, counters, values: [{kind, key, value, first_day, last_day}], tags: [{tag, kind, key, day, issued_at, last_sent}]}`. A tag day is days since 1970-01-01 on the local calendar (`day_of(ts)`, approvals.today's clock); `last_day` changes only when the day does.
  - `rotation="off"` (the constructor's default, so tests and scripts that build their own map keep version 1's behavior): same value, same tag forever; every tag is live and restorable.
  - `rotation="daily"` (`TAG_ROTATION=daily`, the setting's default): a value gets a new tag the first time it is tagged on a tag day, and the roster gets its whole block at once, shuffled with the seed and the day. `[Teacher]` stays fixed (the user) and always restores, sent or not. A tag is live until `grace_hours` after its own day ends (`day_end(day) + grace`): sending it again, or making it late on an older tag day through a view, never extends that, so a Muse that keeps sending a tag back still gets new codes once the window has passed. `as_dict()` is the live tags (the device's own model reads and writes these), `for_muse()` the live tags that were sent to Muse (`touch(tags, now=None)`: sets `last_sent` and saves at once the first time a tag is sent; a later send changes nothing), `expired(text)` the tags in Muse's text that will not restore (bracketed tags of any kind, plus Student and Person references without brackets, a Student one only with one capital letter; never sent, past the window or never made look the same), `day_for(text)` the newest tag day among the restorable tags in `text` or None, `mixed_days(*texts)` True when the restorable tags in `texts` (not `[Teacher]`) come from more than one tag day; each text is read on its own, so no tag runs from one into the next. `view(day=None) -> TagView` pins `tag_for` and `ensure_roster` to one day and passes everything else through. `known_index()` and `known_values()` span every value from every day, so `tag` and `leaks` never get weaker when a tag expires.
  - `purge(now=None, retention_days=None, roster=None, keep=()) -> {"tags": n, "values": m}`: with daily rotation every tag past its window is dropped (the counters keep its code from coming back); with `retention_days`, a value not on the roster whose `last_day` is older than that goes with its tags, unless a live tag (daily) or a tag in `keep` (results still waiting for the user's OK) points to it. Purging twice changes nothing.
  - Upgrade from version 1 on first load: the file and each file in `backup` (base.db, through SQLite's backup API) are first copied next to themselves as `<name>.v1-backup-<YYYYmmdd-HHMMSS>`, 0600 (`TagMap.backups` lists them). Each file is checked on its own: the tag map is not copied again when a copy of the same bytes is there, and a file in `backup` is not copied again when any copy of it is there (`guard.back_up_files(files, now=None)`), so a service that restarts after a failed upgrade does not fill the disk, and a base.db never copied is still copied. Only a usable copy counts (SQLite reads its schema, opened immutable so no -wal or -shm appears): a base.db copy is written as `<name>.v1-copying-<time>` and renamed to its `.v1-backup-` name only when the backup API has finished, a failed one is removed, a killed one is removed by the next copy, and an empty `.v1-backup-` file left by an older start does not count. `Services.create` also calls `services.back_up_db_before_upgrade(paths.db)` before any store opens: one base.db copy when its `audit` table lacks `via` or its `jobs` table lacks `sources` (`NEW_COLUMNS`) and no copy is there yet, so a tag map already at version 2 does not leave base.db uncopied. If that copy fails (an `OSError` or `sqlite3.Error`), it raises `GuardError(services.DB_COPY_FAILED)` before anything changes, so `python -m base` prints "Not starting: ..." and exits 3 as for a failed upgrade. Each v1 entry becomes a value and a tag on today's tag day with `last_sent` = load time, since Muse may hold it; seed, `next_letter` and counters carry over, and the file is rewritten as version 2. A failure leaves the copies and the old file and raises `GuardError(MIGRATION_FAILED)`, a plain message; `python -m base` then prints "Not starting: ..." and exits 3. An unknown version is still "unreadable".
  - Other methods: `tag_for(kind, key, value=None, day=None)`, `ensure_roster(roster, day=None)`, `get(tag)` (any tag the map has), `kind_of(tag)`, `values()`, `today(now=None)`, `save()`, `flush()`. A student's value is the full name.
- Every scan (tag, leaks, find_names, find_identifiers, blocked_topics) runs on a normalized copy of the text and maps spans back: NFKC, format characters removed (soft hyphen, zero-width spaces), every dash as `-`, modifier apostrophes as `’`, `_` as a space, and line-break hyphenation joined. `tag` and `leaks` read `_detection_view(text)`, the same copy with a short list of Cyrillic and Greek look-alike letters (`_LOOKALIKES`) folded one to one, so a respelled name or email is found and its span maps back; it is never written or sent. Only a word whose letters are all Latin once folded changes, and a word with no Latin letter of its own changes only in a text that is mostly Latin letters, so Russian and Greek text is left alone. Name and keyword matches need a non-letter on each side, so `camila_iep_goals.md` shows a name and the `iep` topic. A name in single quotes counts (‘Maya’, 'Maya'); only an apostrophe right after a letter blocks one (the Callaghan in O'Callaghan). A lowercase last name of 4+ letters that is not a common word counts. Identifiers also cover en dashes and non-breaking hyphens, dotted card numbers, `S-401127`, a 9-digit run within 30 characters of ssn/itin/social, and lowercase street addresses with a plain street word. `long_digit_runs(text)` lists runs of 7+ digits (alone or joined by `-` or `.`) that are not dates. `name_occurs(name, text)` is the flexible check the model's name pass uses, and `occurring_names(name, text)` gives the name if it occurs, else each of its words that does.
- `tag(text, roster, tagmap, llm_names=None, never_share=None) -> TagResult`: identifiers, roster names, every real value already in the tag map, then names from `llm_names(text)` (the local model's second pass) as `[Person N]`, lowercase ones included. Longest span first, never inside a tag, re-scanned until clean. If `llm_names` raises, so does `tag`. A `TagMap` is pinned to today's tag day for the whole call (`tagmap.view()`; a `TagView` keeps its own day), so one text never mixes two days' tags. How model-found names are tagged:
  - A trailing possessive or punctuation is dropped from each name ("Bennick's" and "Cinderfall." count as the bare name).
  - Each word of a model name is also tagged alone, with its own `[Person N]` (a later "Bennick" when the model reported only "Bennick Cinderfall"), and so is each 3+ letter piece of a hyphenated word. Titles, the suffixes jr, sr, ii, iii and iv, and particles (de, la, van) that are lowercase or not the first word are left out. Any other lowercase word counts ("Bennick cinderfall").
  - A name or word that is also a common word (Mason, Grace, May) is tagged only where the text capitalizes it and does not use it as the word, with the roster's rules: not before a subject pronoun ("Will you"), not after a determiner, and a month not next to a number or after "in" ("May 5"). A known value that is a common word follows the same rules in later texts. A common word under 3 letters, a pronoun, a determiner or a title is never tagged from the model pass, and a name whose words are all roster forms, or a word that is one, is left to the roster pass.
  - A one-word name the model reported on its own, not as a word of a longer name it also reported, takes in up to two capitalized words on each side, only where the text capitalizes the name and only across spaces or tabs (not a comma or a line break): "Cinderfall" alone still tags "Bennick Cinderfall". Each word it takes in is tagged alone where the text capitalizes it. This is one step: a word taken in takes in nothing more. A word is not taken in when it is a common word, a title, a roster name, one letter, touches a digit or an identifier (the "S" of S401399), is in capitals next to a name that is not (IEP), is written in lowercase elsewhere in the text, or is a greeting, label or role word (Hi, Overall, Nurse, Contact; `guard._NOT_NAMES`). A possessive ends the name before its 's ("Ona Thistlewood's group" tags "Ona Thistlewood"). A name the model reported with two or more words takes in nothing.
  - Every value the model pass gave (the reported names, their words, a fuller name and the words it took in) is stored in the tag map as a known value, also where a longer span covered it in this text. A common word is stored only where it was tagged alone. So a later text with only "Bennick" or "Cinderfall" is tagged with no model call, and `leaks` (egress final_check) reports it.
- `restore(text, tag_map)`: tags back to values, tolerant of `Student A`, `student a`, `Student A's`, `(Student A)`; a Student code of two or three letters restores only in brackets (`[Student AB]`), since "student is", "Student ID", "Student IEP" or "STUDENT OF" are words as often as codes and daily rotation makes most such codes real. Without brackets "student" and its letter must be on one line (spaces or tabs between them), and a dot and a letter after the code make it an abbreviation ("Student I.D.", "student e.g.", "i.e."). Lowercase "student a" and "student i" count only before a word or mark that shows a reference (`_REFERENCE_AFTER`). An unbracketed capital code still restores (Ethan, Oct 31), so "the student I flagged" reads as `[Student I]`; see THREAT_MODEL residual risks. Accepts a dict or a TagMap (its `as_dict()`, the live tags). Muse's text is restored with `for_muse()` (Connector). `tag_references(text, *, as_written=False) -> [(tag, bracketed)]` lists every tag `restore` would swap, in canonical form, by the same rule (so `day_for` and `mixed_days` agree with it); with `as_written` (what `TagMap.expired` uses) an unbracketed Student reference counts only when its letter is a capital, so "each student who has" or "the student was" is never refused as a guessed tag.
- `neutralize_tags(text, tagmap)`: every `TAG_RE` match in `text` becomes a `[Redacted N]` tag (kind `term`, key `literal:<text>`) whose value is that literal text, so a document that says "[Student B]" or "[Teacher]" never reaches Muse as a real person's tag, and restoring it gives back the words. Known-value scans skip tag-shaped values. "Student B" without brackets is left as written (a residual: Muse can still read prose that way).
- `blocked_topics(text, never_share)`, `blocked_reasons(text, never_share)` (wording in `TOPIC_REASONS`, else "Mentions <topic>"), `leaks(text, roster, tagmap) -> list[Hit]` (used by egress and the eval): everything tag() would find plus full names of 8+ letters spelled run together, letter by letter, slugged or reversed, so final_check is stricter than tag().

## Model clients

`base/local_llm.py`:
- `LocalLLM(settings, role="answer"|"router", *, client=None)`. The httpx client has `trust_env=False`: no environment or system proxy. `chat(messages, *, max_tokens=2000, json_schema=None, tools=None, tool_choice=None, reasoning="low", adapter=None, timeout=None, synthetic=False)` (timeout None: 120 s, or on llama_server `max(120, max_tokens / 5 + 60)` s; connect 10 s; a read timeout on llama_server is not retried) -> ChatResult(content, tool_calls, reasoning_tokens, prompt_tokens, completion_tokens, latency_ms, model, finish_reason, provider, calls=1)`. `last_result` (thread-local) is the ChatResult of this thread's last `chat` or `chat_json` call with every try added up (`calls` 2 after a cut-off reply's retry or a bad-JSON retry; `merged(first, second)`), or None when that call failed before any reply.
- On a cloud backend every call must pass `synthetic=True` or it raises `CloudBackendRefused`. openrouter sends `reasoning: {"effort": ...}`; llama_server sends `chat_template_kwargs.reasoning_strength` and, with `adapter`, `lora: [{"id": int, "scale": 1.0}]` (an adapter on openrouter is a `ValueError`). A `Reasoning strength:` line is added to the system prompt if missing. A reply cut off with no content is retried once with double the budget, then `LLMTruncated`.
- `chat_json(messages, schema, **kw) -> dict` (schema plain or `{name, strict, schema}`), one retry, then `LLMParseError`. Both subclass `LLMError`.
- `llm_names(text, *, synthetic=False, max_tokens=1500) -> list[str]`: names Glimmer finds, kept only where they occur in the text (`guard.occurring_names`: apostrophe, space and case differences allowed). ## Workspace (`base/workspace/`)

- `index.py`: `DocumentIndex(settings)`: `list(folder) -> list[Doc(id, path, title, size, modified)]` (recursive; `id` and `path` are the POSIX path relative to the workspace root, never absolute; `title` is the first markdown heading or the file stem), `read(doc_id) -> str`, `search(query, k=5, folder=None) -> list[Snippet(doc_id, title, text, score)]` (BM25 over .md/.txt, no embeddings), `resolve(name)`. Titles are found with a linear pattern on the first 2000 characters. list and search also check the marker on each file's resolved folder. `passages(queries, k=20, folder=None) -> list[Snippet]`: every readable document cut into ~800-character pieces (150 overlap), each piece ranked by BM25 and, with an embedder, by meaning, for every query; reciprocal rank fusion over all those rankings, at most 3 pieces per document, `Snippet.text` the whole piece. The meaning ranking counts only its `MEANING_TOP` (5) closest pieces per query, so past those a piece needs a keyword match (every piece has some similarity, and counting them all let unrelated files fill every slot). `Rag.queries(question)` is the question plus up to 3 queries the checker writes (tags restored, the question alone if the call fails); `Rag.retrieve(index, question)` is `index.passages(queries)`. search_documents uses retrieve then `Rag.pick`, and sends up to 600 characters of each picked passage, centered on the query words; without the checker it keeps `search` and 300-character snippets. A PDF's or image's title is its file name with `_` as spaces. Hidden files, files over 5 MB and links out of the root are skipped. `.pdf` files are documents when `pdftotext` is installed (`PDFTOTEXT_BIN`, else PATH): their text layer, read on the device and cached until the file changes; a PDF that will not read is skipped in search. With `SEARCH_EMBEDDINGS=1` the index gets an `Embedder` (`base/workspace/embed.py`, EmbeddingGemma 2 on this device's llama-server, `EMBED_URL` loopback only, `scripts/start_embedder.sh`, port 8084): each document is cut into overlapping 1200-character pieces, a document's meaning score is its best piece's cosine to the query, and the BM25 and meaning rankings are fused by reciprocal rank (k = 60). A document found only by meaning shows its closest piece as the snippet. If the embedder fails, search is BM25 only. A missing folder raises `FileNotFoundError`; `..`, `~` or an absolute path raises `WorkspacePathError` (a ValueError).
- `jobs.py`: `JobStore(db)`, table `jobs(id, kind, instructions, folder, status, created_at, finished_at, result_kind, raw_result, summary, approval_id INTEGER, error, model_log, release_status, released_text, topics, sources)`. Status `queued, running, waiting_for_approval, done, refused, failed`; release status `none, releasing, shared, waiting, refused`. Methods: `create(kind, instructions, folder) -> id`, `start`, `set_status`, `set_kind`, `add_model_step`, `finish(job_id, raw_result, result_kind, summary=None, topics=(), sources=())`, `job_for_result(kind, instructions, raw_result, result_kind, sources=()) -> id` (a finished job written as status `done` in one insert, so it never counts toward MAX_ACTIVE_JOBS; the connector uses kind `search` for search_documents results; returns the newest identical job instead, same kind, instructions and raw_result and not failed, while its release status is none, releasing or waiting; a returned job that has no sources yet gets these), `fail`, `set_release(job_id, status, approval_id: int | None = None, released_text=None)`, `get(job_id) -> dict | None` (model_log, topics and sources decoded, approval_id an int), `list_recent(limit=20)`, `claim_release(job_id) -> bool` (none to releasing; one caller wins), `reset_release(job_id)`, `fail_unfinished(error) -> int` (queued and running jobs become failed with "The device restarted before the job finished.", releasing goes back to none; Services.create calls it), `active_count()`. `set_release` moves a finished job to `waiting_for_approval`, `refused` or `done`; a failed job stays failed. `error` holds fixed messages only, never exception text. `sources` (JSON list, default `[]`, added on open) are the workspace paths a result came from: a search's passages and an ask job's reading, so the user's controls apply the same way when the release runs after a restart.
- `agent.py`: `Agent(settings, llm, index, jobs, heavy=None, roster=None, tagmap=None, restore=None)`. `run_private_task(instructions, folder) -> job_id` starts a daemon thread, or raises `AgentBusy` when `MAX_ACTIVE_JOBS` (5) are queued or running; jobs take one model slot at a time on the device, two on the cloud backend. `run_sync` finishes first. `stop()` makes queued model steps fail at once (Services.close calls it). It stores Muse's tag-only instructions and restores tags locally only to choose what to do. The model gets Muse's instructions with their tags and every document, title and rubric with roster names, known tag-map values and identifiers swapped for the same tags; its answers are restored to real names on the device. It grades when the instructions mention grade/feedback/score/rubric and a `rubric.md` is in the folder or the nearest parent folder inside the workspace root (`demo/rubric.md` for `demo/essays`). Grading: one strict-JSON step per essay (`grade:<n>`, scores 1 to 4 for ideas, organization, evidence, conventions, total recomputed), all grades before any file, then `<Student Name> feedback.md` (0600) under `settings.paths.output / job_id`, a raw per-student table with real names for roster students and `Essay N` for anyone the roster does not know (`per_student`, topics `grades, writing`) and a class summary with names scrubbed. Up to 4 steps at once on the cloud backend, 1 locally. `model_log` entries are `{step, model, backend, device, latency_ms, via: local|heavy}`. Emits `working`, then `idle` when no job is left.

The connector passes `restore_tags` and `policy.never_share`, then runs `check_tags` on every item's for_tag, title and body, each on its own, before anything is written. `write(out_dir, items, address_to, purpose, *, restore, contacts) -> Saved(files, items, students, no_guardian, drafts)` restores every tag; with `guardians` it writes one unsent email draft (`.eml`: To, Subject, `X-Unsent: 1`, `{guardian}` replaced by the guardian's name) per guardian of the item's student, and skips (and counts) a student with none; with `none`, one `.md` per item. File names go through `agent.safe_filename` and stay in `out_dir`; files are 0600 through `agent.write_private`. `merge.csv` lists file, for_tag, student, guardian, email, title and purpose (cells that could start a formula are quoted), plus a row with no file and guardian `none on file` (`NO_GUARDIAN`) for each item whose student has no guardian on the sheet. The list there shows who each one is for and any with no parent on file."), never the number of letters or of students with no guardian, which one call per student would turn into each family's size; those stay in merge.csv. `SAVE_REQUEST` is the fixed request egress sees for it.

## Regions sidecar (`sidecars/sam/`)

Meta's SAM 3.1 on this device behind a small HTTP server, so faces, signatures, ID cards and barcodes in a page image can be found and covered before the local reader sees the page. It has its own uv project (`sidecars/sam/pyproject.toml`: mlx-vlm, pillow, fastapi, uvicorn; `exclude-newer` set to Oct 16 keeps the lock to releases at least two weeks old), so the root project never imports mlx. As of Oct 31 nothing is locked or installed and no weights are on disk; the mlx predictor is unverified (see `sidecars/sam/README.md`). The device side that calls it is in Regions on the device, below.

- Start: `scripts/start_sam.sh`, which does nothing unless `SAM_ENABLED=1` (default off). `scripts/start.sh` runs it when `SAM_ENABLED=1` as an optional helper under `keep_running` (see Starting and staying up), never `require`: it starts before the app, the app does not wait for it, then, after the relay client has started, start.sh waits up to 180 s for its `/health` (`wait_up`, which stops early once the SAM loop has stopped) and says whether it came up (log in `BASE_HOME/logs/sam.log`). It stopping never stops the app; it is started again with backoff, and images are not read (fail closed) until it is back. Missing weights or a missing sidecar environment exit 3, so the retries stop. `SAM_URL` (default `http://127.0.0.1:8085`, read through `Settings.sam_url`) must be loopback; `SAM_MODEL_DIR` (default `models/sam3.1-mlx`) must hold the weights' `config.json` and `sidecars/sam/.venv` must exist, or it prints what Ethan would run and exits without downloading or installing anything. It sets `HF_HUB_OFFLINE=1` and runs `python -m sam_server --host 127.0.0.1 --port <SAM_URL port> --model-dir ... --model <SAM_MODEL_ID, default mlx-community/sam3.1-bf16> --key-file BASE_HOME/llama_api_key`. `sam_server.main` refuses any host but 127.0.0.1, ::1 or localhost, and a missing or empty key file.
- `GET /health` (no key): `{ok: true, model, backend: "mlx" | "fake", prompts_version, concepts}`. A caller treats `backend: "fake"` as no checker.
- `POST /regions` with `Authorization: Bearer <key>` (the key in `BASE_HOME/llama_api_key`, compared in constant time; 401 otherwise). Body over 8 MB, by Content-Length or while streaming: 413. JSON body: `image_b64` (PNG or JPEG, at most 40 MP), `concepts` (default all of `face`, `signature`, `id card`, `barcode`), `threshold` (0 to 1, default 0.3), `pad` (0 to 64 px, default 8), `cover` (default true). A bad body is 400 with a fixed `{error}` that never repeats the input. Reply: `{width, height, model, prompts_version, regions: [{kind, concept, score, box: [x1, y1, x2, y2]}], counts: {kind: n}, pad, covered_png_b64, ms}`. Kinds are `face`, `signature`, `id_card`, `barcode`; boxes are pixels with x2 and y2 exclusive, clipped to the image. `covered_png_b64` is the page with each box grown by `pad` (clipped) filled solid black, a box fill rather than the mask so it fails safe; it is left out with `cover: false`. A model error is 500 with fixed text, and the log gets the exception's type name only.
- One check at a time behind a lock. The image is never written to disk or logged: the one log line per request is the counts and milliseconds.
- Predictors (`find(image, concept, threshold) -> list[Region]`): `MlxSamPredictor(model_dir, model)` imports mlx-vlm only when built and sends each concept's prompts (`PROMPTS`, `PROMPTS_VERSION` "v1"; barcode also asks for "qr code"), keeps boxes and scores above the threshold (`regions_from_output` accepts pixel or 0 to 1 boxes) and drops a box that repeats a better one of the same kind (IoU 0.7). `FakePredictor(truth_path)` answers from `eval/sam_pages/truth.json` by matching the decoded pixels to a page, score 1.0; any other image has no regions. Tests use only the fake (`tests/test_sam_server.py`, `tests/test_regions.py`).

## Regions on the device (`base/regions.py`)

With `SAM_ENABLED=1` (and `CHECKER_BACKEND=lfm`, so images are documents at all), every page image is covered by the sidecar before LFM3-VL-2B reads it, and an image the sidecar cannot check is not read. Off by default: with `SAM_ENABLED` unset nothing here runs and images are read as before.

- `RegionClient(settings, *, client=None, allow_fake=False)`: httpx with `trust_env=False`, 60 s timeout (connect 5 s), refuses a non-loopback `sam_url`. The key is `settings.checker_api_key` (the same `BASE_HOME/llama_api_key`). `check(image_bytes) -> Regions(sha, counts, boxes, model, prompts_version, covered)`. A cache hit makes no call. Otherwise it first needs `GET /health` to say `ok` with backend `mlx` (a good answer counts for 60 s; `backend: "fake"` is refused unless `allow_fake`, which only tests pass), then `POST /regions` with all four concepts, `pad` 8 and `cover: true`. Counts are recomputed from the regions; every kind must be known, every box inside the page, and the covered copy a PNG the size of the page. Anything else (no key, down, slow, 4xx/5xx, a bad reply) is `RegionError` with the fixed text `UNCHECKED`. After the sidecar was down or slow (an httpx transport error), every check fails at once for 30 s instead of waiting again; an error status or a bad reply fails that image only. `available()` (the Controls page) is a 2 s health check.
- Cache, under `BASE_HOME/regions` (0700): `<sha>.json` (`version` 1, `counts`, `boxes`, `model`, `prompts_version`, `pad`; no pixels) and `<sha>.png` (the covered copy, never the original), both 0600, written atomically, the PNG first. `read_record(folder, sha)`. Retention deletes both (`retention.purge`).
- `ScanReader(settings, llm, *, regions=None, controls=None)` (`base/workspace/scans.py`; `covering()` says whether a page goes to SAM first right now): with a client, the vision model gets only `Regions.covered`, and the text ends with `covered_note(counts)` ("Covered on this device before reading: 2 signatures and 1 photo of a person.", or "Checked on this device before reading: no faces, signatures, ID cards or barcodes found."). That text is cached as `<sha>.covered-v1.txt`, so a `<sha>.txt` read without covering is never reused. The check runs before the cached text is used (a cache hit when the record is there), so every covered reading has its record. A `RegionError` becomes `ScanError(UNCHECKED)` with no model call and nothing cached; the index already skips an image that raises, so it is in no search, passage, ask or task, and `index.read` raises. Under the `cui`, `cjis` or `export` toggle (or a broken controls file, which reads as every toggle) SAM is never called: the SAM License excludes ITAR and military end uses, and those toggles already keep every result on the device, so the page is read as it is under the plain `<sha>.txt` name.
- Saying so: `unchecked_images()` is a context manager that collects the images the reader left out (`note_unchecked`, in memory only). `search_documents` (base/connector/server.py) and `DeviceAsk.run` (base/workspace/ask.py) add `unchecked_note(n)` ("2 images were not read, because the device could not check them for faces and signatures first.") to what they return. A `run_private_task` that hits one fails with the same fixed `UNCHECKED` text (`agent.short_error`).
- Lookups for egress and the page: `image_sources(sources)`, `image_check(settings, sources) -> ImageCheck(counts, checked, unchecked) | None` (None when no source is an image; an image whose current bytes have no record counts as unchecked, so a changed or missing file is unchecked), `covered_png(settings, doc_id) -> Path | None` (only files in `BASE_HOME/regions` with a record), `workspace_file(settings, doc_id)` (inside the root only), `describe(counts)`.
- Egress, only with `SAM_ENABLED=1` (otherwise receipts and floors are unchanged): for every kind but `document_list` (a listing never reads an image), `image_check` on the release's sources. The receipt gets `image_regions` (kind to count) and `images_unchecked`, and its `checks` gain `image check` when at least one image was checked. No box, pixel, file name or hash is in the receipt. With `SAM_ENABLED=1`, an image source with no record refuses the result (floor `regions:unchecked`, "Kept on your device. It came from an image the device has not checked for faces and signatures."), unless a toggle already refuses it with its own reason. `compliance.check(..., image_kinds=counts)`: see Compliance toggles.
- Approval page: `GET /scan-preview/{decision_id}/{n}` serves the covered PNG for the n-th image source of that decision row (`sources`), behind the same access as every page (a session off loopback). 404 for a deleted row, a bad index, a source that is not an image or has no covered copy. It never reads anything but `BASE_HOME/regions/<sha>.png`. The approval card shows each covered page as a thumbnail with "Covered on this device before reading. The covered page stays on this device: Muse gets text only, never the image." History's receipt has an "Image check" line, `/api/audit.csv` an `image_regions` column (`kind=n;...`), and the Controls page one line while `services.regions` is set and its sidecar is not answering.

## Privacy controls (`base/controls.py`)

- Set on the approval page's Controls tab (GET `/controls`, POST `/api/controls` as a form or JSON, GET `/api/controls`), kept in `BASE_HOME/privacy_controls.json` (0600), re-read when the file changes; a broken file means the default, which tags everything. `Services.controls` is the `ControlStore`.
- `Controls(tag_kinds, always_redact, never_redact, names_off_folders, hidden_folders)`. `tag_kinds` covers phone, email, address, dob and student_id; SSNs and card numbers are always tagged. Folders are top-level names, `.` for the files at the top of the workspace.
- `Controls.redaction(sources) -> guard.Redaction | None`: `guard.Redaction(skip_kinds, names, always, never)` is passed to `guard.tag` and `guard.leaks` (the final check), so both agree. `always` words become `[Redacted N]` tags (kind `term`, also in `TAG_RE` and restore); `never` words are left as written wherever they occur, except inside an SSN or card number; always wins over never. Names are left as written only when every source of the result is in a names-off folder (then the model name pass is skipped too); no sources or mixed sources tag everything.
- Egress: `release(..., sources=())` sets the redaction for that release (a context variable), and the decision row keeps `sources` (column added on open), so `resolve` after the user's OK checks with the same controls. The connector passes the listed documents (list_documents), and for a job the row's `sources`: search_documents' picked passages, and every candidate passage the model was shown when it wrote an answer (`Rag.pick` sees them all, so the answer can draw on any); ask_device's reading; a run_private_task's documents (`Agent._work`: the essays and the rubric when grading, every document otherwise). Only a job with no sources (from before the column) falls back to its folder. They live in the job row, so a release after a restart uses the same controls, toggles and image checks (a names-off folder, a scanned page); a job with no sources and no folder tags everything. With `SAM_ENABLED=1`, an image a search, ask or task read while covering was off (`regions.reads_uncovered(index)`, checked when it starts and ends: a `local_only` toggle or a broken controls file keeps SAM out) is stored as `regions.UNCOVERED + doc_id` (`mark_uncovered`), which `image_check` always counts as unchecked, so the result is kept (floor `regions:unchecked`) even after that toggle is turned off.
- `hidden_folders`: `DocumentIndex(controls=...)` skips every file in them, and `resolve` raises `FileNotFoundError` for a hidden folder, so list, read, search, passages, ask_device and tasks all lose them.

## How learned rules are used (`base/router.py`, `routing_mode`)

With `DEVICE_ONLY=1` the Dreaming page (POST `/api/learning`, `Controls.learning`) or `DREAMING_BACKEND` and `ROUTER_TRUST` pick one mode:

| Mode | Env | What decides |
|---|---|---|
| rules | `DREAMING_BACKEND=rules` (the default) | A rule the user taught, else the policy. No model call. |
| tighten | `prompt`, `ROUTER_TRUST=tighten` | That decision, or the model's when it is stricter. |
| decide | `prompt`, `ROUTER_TRUST=decide` | The model, with the rules in its prompt, under the floors. |
| local_lora | `local_lora` | As decide, with the adapter at `BASE_HOME/adapters/router.gguf`. Needs `PRIMARY_MODEL=glimmer`. Training one on the device is not built, on Ethan's Oct 30 instruction not to test Glimmer fine-tuning yet. |

A compliance toggle sets `RouteInput.strict`, which turns decide and local_lora into tighten without the adapter. `DREAMING_BACKEND=lora` is refused with `DEVICE_ONLY=1`, because its training examples leave the device. A device-only Glimmer uses one llama-server for answers and routing.

## Compliance toggles (`base/compliance.py`)

- `/ask` answers a question with the device's model only (`ask_runner`, no egress), showing real names on the page. It is how a `local_only` user gets answers. `GET /ask?job=<id>` shows a job only when its kind is `ask` and its request is `ui_app.PAGE_ASK` ("asked on this device", what POST `/ask` stores); any other id gives the empty page, so a Muse task's or search's raw result never renders there.
- Retention (`base/retention.py`, docs/RETENTION.md): `retention_days` (90 under COPPA and GDPR), run at most hourly from the release path. `purge(services, days, now=None)` deletes decided rows, finished jobs, finished files, scan text, image checks (`regions`: region boxes and covered copies) and, through `TagMap.purge(now, days, roster, waiting_tags(services))`, tag map values and their tags; it returns counts for `decisions, jobs, files, tags, values`. `expire_tags(services, now=None)` drops tags past their grace window with no toggle, keeping the tags in pending approvals (`waiting_tags`); `maybe_purge` runs it at most hourly (`maybe_expire_tags`) before the toggle check, and `Services.create(owner=True)` runs it once at start.
- No page may say "compliant". Each profile's `limit` is shown next to its toggle.

## Guardian PIN (`base/guardian.py`)

- For a device set up for a family member. `Guardian(home, clock=time.time)` keeps a salted PBKDF2-SHA256 hash (200,000 rounds) in `BASE_HOME/guardian.json` (0600), never the PIN. `set(pin, *, approvals, token=None)` (6 to 64 characters; changing an existing PIN needs an unlocked `token`), `remove(token)`, `verify(pin)`, `unlock(pin) -> token | None` (10 minutes, held in memory, so a restart locks every browser), `lock(token)`, `unlocked(token)`, `allows(token)` (no PIN, or unlocked), `allows_approval(token)` (`approvals` off, or unlocked). `MAX_MISSES` (5) wrong tries lock the PIN for `LOCK_SECONDS` (15 minutes), counted in the file; while locked, `verify` raises `GuardianError`.
- The approval page: the `muse_guardian` cookie (HttpOnly, SameSite=Strict, Secure with TLS) carries the token. While a PIN is set and the browser is not unlocked, POST `/api/controls`, `/api/setup`, `/api/learning`, `/api/auto-approve` and `/api/history/{id}/delete` answer 403 (`guardian.LOCKED`). POST `/api/approvals/{id}` with approve true answers 403 (`APPROVE_LOCKED`) when `approvals` is on, and approve with remember answers 403 whenever a PIN is set, since "don't ask again" is a standing rule. Deny, with or without remember, never needs the PIN. POST `/api/guardian` (`pin`, `pin_again`, `approvals`, or `remove`) sets, changes or removes it and leaves the browser that set it unlocked; POST `/api/guardian/unlock` (`pin`; 403 wrong, 429 locked out) and `/api/guardian/lock`. The Setup page shows the section outside its main form, and Approvals and Controls say when the lock is on.
- It guards against the family member changing the rules at the device, not against someone with an administrator account, who can delete the file. It does not see what anyone types into Muse.

## Router (`base/router.py`)

Request labels: `lfm_labels(settings)` is True with `DEVICE_ONLY=1` and `CHECKER_BACKEND=lfm`, which is LFM labeling Muse's requests whichever model decides (the plug-in settings, `PRIMARY_MODEL=glimmer`, included). Then egress passes the labels through `checked_labels(request, labels, class_of=loosened(settings, "class_of"))` (a whole text must be asked for, a question about one tagged person is not class-level, a class-level question gets `class_level`), so every router configuration routes on the same checked labels and a model comparison differs only in who decides. With `CHECKER_BACKEND=glimmer` Glimmer's labels are used as they come.

With `DEVICE_ONLY=1` and LFM, no model decides: a rule the user taught, else the first matching policy rule, gives the decision (`source="rule"`). Practice defaults only count as floors, never as permission to share. The model only labels who a request is for. More floors apply there: a `sensitive_record`, a request for contact details (floor `contact`) and a request that picks out one person by what makes them unique (floor `narrowed`) are refused, and a request that names a destination outside the class gives ask_user (floor `outside_class`) unless a rule the user taught shares results like this. A router that could not decide (`source="fallback"`) is never answered by Always approve, and neither is a card with a floor in `approvals.AUTO_APPROVE_SKIPS` (see Approvals).

- `Router(settings, llm, policy, rules_text=None, adapter=None)`, `decide(inp, *, synthetic=False) -> RouteDecision`. `rules_text=None` re-reads `settings.paths.router_prompt` on every call.
- Rule path, no model call: `document_list` with a `person` hit (the name pass found someone the roster does not know) asks the user, unless `ROUTER_LOOSEN=lists` and the user taught a share tagged rule for its exact `(document_list, topics)` group (the shown learned rule, source `user`; a practice default never counts): then it shares tagged, names still tags, floors and the final leak check unchanged; otherwise `document_list` and `dreaming_report` share tagged; a policy rule marked `pre_approved` (matched on request, kind and topics) when nothing is blocked. Otherwise one strict-JSON call (`ROUTE_SCHEMA`, reasoning `settings.router_reasoning`, `settings.router_max_tokens` tokens; `Router.reasoning()` and `Router.max_tokens()`, defaults low and 1500) with the system prompt, the learned rules and the RouteInput (hit kinds only, real values scrubbed, text cut at 1500 characters). `system_prompt()` sets its `Reasoning strength:` line to the same level, so the prompt holds exactly one such line and it agrees with llama-server's `chat_template_kwargs.reasoning_strength` (LFM's request drops the line). The decision carries the call's usage (`model_usage(llm)`, from `LocalLLM.last_result`; a client that keeps none counts one call and no tokens).
- Rules mode's policy path adds topic words for the policy match only (never stored or sent): `writing` and `grades` from the request's words, and with `ROUTER_LOOSEN=result_words` also from the tagged result (`result_topics(tagged_text)`: `grades` for a score, `scored`, `points`, `rubric`, `out of N` or `N/M` that is not part of a full date; `class_level` for class-wide numbers such as an average, a median, a percent or "18 of 24 students" in a result with no `[Student X]` or `[Person N]` tag). An ask word (attendance, absent, tardy, seating, sits, reading group, lunch, behavior) in the request vetoes all of them, and one in the result vetoes the result's. `_OUTSIDE` (floor `outside_class`) also catches sending something home ("send it home", "a note home", "take it home").
- Contact and narrowed floors (`router._CONTACT`, `router._NARROWED`) read the tagged request and need no model. A first word the guard tagged (`[Person N]`, RED-F1b) stands in for "Email for" and "Exactly one". The newer contact wordings need a tag, so a draft ("an email for [Student A]'s mom") or a mention of a phone or a parent passes. `singles_out(sentence)` is `_NARROWED` plus `_SUMMARY_NARROWED` ("only one student", "the student with", "one student who"), used on summary sentences by egress.
- Left-out floor (`router._LEFT_OUT`, floor and code `left_out`, not model mode): a request that leaves out a tag or a named group, table, team or pod, on a `class_aggregate` result or a class-level request, asks the user, whatever the user taught, because two answers subtract to that one's number. Always approve leaves it for the user (`approvals.AUTO_APPROVE_SKIPS`).
- `checked_labels(request, labels, *, class_of=False)`: with `class_of` (egress passes `ROUTER_LOOSEN=class_of`), "[Student A]'s class" or "[Student A]'s group" does not count as a question about one person, so a `class_level` label stays. `loosened(settings, choice) -> bool` reads ROUTER_LOOSEN.
- Reason codes (`RouteDecision.code`), one per decision, for what decided it; when a floor ties the path's decision the floor's code wins, as its reason does. Rule path: `unknown_person_title`, `learned:share_tagged` (a taught list rule), `rule_kind`, `pre_approved`. Policy path: `learned:<decision>` (your rule), `policy_rule:<id>`, `policy_default`. Model: `model`, `fallback`. Floors: `blocked:<topic>` (or `blocked`), `ask_first:<topic>`, `request_topic:<topic>`, `identifier:<kind>` (the first in sorted order), `identifier:digits`, `policy_rule:<id>` (a refuse rule), `learned:<decision>` or `practice:<decision>` (a practice default), and whenever routing is not model mode (rules, tighten, decide and local_lora with DEVICE_ONLY=1: `Router.decide`'s `by_policy`, after the rule path) `sensitive_record`, `contact`, `narrowed`, `outside_class`, so lfm_tighten and lfm_decide rows carry them too. Egress sets `compliance:<floor>` for a toggle's hold and `name_check`, `topic_check`, `summary`, `compliance:cloud` for its own holds. `scripts/ask_causes.py` counts asks by them.
- Floors on every path: a blocked reason or a never-share topic of the result -> `refuse`, or at least `ask_user` when every blocked topic is in `ask_first` (`never_share_floor(blocked, blocked_topics, ask_first) -> refuse | ask_user | None`, which egress also uses); a never-share topic only in Muse's request (`request_blocked`) -> at least `ask_user`, never `refuse` by itself, since "Do not mention any IEP" is a caution, not a question; an identifier hit -> at least `ask_user`; a model or parse error -> `ask_user`, source `fallback`. Also: a long digit run (`guard.long_digit_runs`) in anything but `class_aggregate` and `dreaming_report` -> at least `ask_user`; every policy rule that wants `refuse` and matches the request, kind and topics -> `refuse` (a rule over never-share topics only is the blocked floor already); the learned floor (`train.learned_floor`, below) -> at least its decision. When a floor decides the result, its fixed reason replaces the model's. Floor labels: `blocked:<topic>`, `ask_first:<topic>`, `request:<topic>`, `identifier:<kind>`, `identifier:digits`, `policy:<rule id>`, `learned:ask_user`, `learned:refuse`, `blocked`, plus egress's `summary`, `name_check` and `topic_check`.
- Learned rules (the dreaming file, keyed with `train.rule_key(kind, topics, relevant_topics(policy))`): the model is shown the one rule that fits best (`train.match_rule`) on a "Learned rule for this result" line. The learned floor is computed apart from it: the strictest `ask_user` or `refuse` rule among the shown rule and every rule that covers the result (`train.covers`: a rule for the same kind whose topics are a subset of the result's, `topics: none` included, or a matching `(topic: X)` rule), counting your rules first and practice defaults only when none of your rules covers the result. So a topic Muse's request adds (`class_level`, `parents`) can move a result to a narrower group but never out from under a broader ask first or refuse rule, and a closer share rule never loosens one. When the floor's rule is not the shown one, the model also gets a "Learned rule that also holds" line, and the system prompt's step 3 says to follow it.
- `build_user_message(inp, learned=None, also=None)`. `Router.learned(inp, rules=None) -> (shown, floor)`, each a `train.RuleLine` or None; `Router.learned_rule(inp)` is the shown one. `Router.learned_view(inp, rules_text=None) -> LearnedView(shown, floor, floor_decision, floor_source)`, a hashable NamedTuple of the shown rule line, the floor's rule line, its decision and its section (`user` or `synthetic`): everything the learned rules add to one decision, for the given rules text (default: the router's own), so the gate can compare two rule files item by item. router.py imports `base.dreaming.train` and `base.guard`.

## Approvals (`base/approvals.py`)

- `ApprovalStore(db_path)`, SQLite WAL behind one lock. Table `decisions(id, ts, day, job_id, tool, request, result_kind, topics, blocked, tagged_text, shown_form, router_decision, router_reason, router_source, status, user_decision, remember, decided_by, decided_at, deleted, item_id)`. Ids are ints. `blocked` is a JSON list of plain reasons from `TagResult.blocked`; the approval page shows it as is. Older dbs get the column on open.
- `record_auto(**kw) -> id` and `create_pending(**kw) -> id` take keywords `tool, request, result_kind, tagged_text, router_decision` and optionally `router_reason, router_source, topics, blocked, shown_form, job_id, day (default today(): days since 1970-01-01), item_id`. `decide(id, approve, remember=False, by="user"|"policy_sim")` returns the row; `KeyError` for no row, `ValueError` if it is not pending or was deleted. `get`, `pending()`, `history(limit=50)` (both skip deleted rows), `delete(id)` (deleted=1, request and tagged_text blanked), `training_rows()` (decided, not deleted, with `label`), `counts_by_day()` (rows that were not auto, per day), `close()`.
- `label_for(row)`: approve + remember -> `shown_form`; deny + remember -> `refuse`; no remember -> `ask_user`; undecided -> None.
- `wait_decided(id, timeout) -> bool`: waits while the row is pending, True once it is not (decided, deleted or gone), False at the timeout. `decide` and `delete` notify a `threading.Condition` on the store's lock after they commit (`decisions_made` counts the notifications), and the wait also re-reads the row every second, so an answer from another process is seen. The connector's `get_result` uses it for `wait_seconds`.
- The approval page shows the exact tagged text, the router's reason, the blocked reasons, Share it / Keep it here and the remember box.
- Always-approve mode (`AutoApprove(path, *, hours=AUTO_APPROVE_HOURS, clock=None)` on `settings.paths.auto_approve`, a 0600 file in BASE_HOME, switched on the approval page with POST `/api/auto-approve {on}`, same-origin like every POST): egress still creates the pending row for an `ask_user` result, then decides it at once with `by="auto_approve"`, no remember, and returns it shared (audit `auto_approved`). Refusals, held results and the final leak check are unchanged. `training_rows()` leaves auto-approved rows out, so dreaming never learns from them.
  - It never answers a card the router could not judge (`source="fallback"`), any card while a compliance toggle is on, or a card with a floor that starts with one of `AUTO_APPROVE_SKIPS`: `request:` (a never-share topic in Muse's request, such as "Which students have an IEP?" over a list of tags), `ask_first:`, `identifier:` (`identifier:digits` too) and `outside_class` ("to send to the principal"). `needs_a_person(floors) -> bool` is that check; those cards wait for the user (audit `auto_approve_skipped`). Other ask cards (a policy rule or default that asks, `learned:ask_user`, an unknown name in a listing) are still answered.
  - It turns itself off `AUTO_APPROVE_HOURS` (8) after it was turned on. `set(True)` writes `on since <local time>` and `started <epoch seconds>`; `since()` reads `started`, else an older file's `on since` line, else the file's modified time. `until()` is the time it turns off, or None; once it is past, or the stamp is more than a minute in the future, the file is removed and it reads as off. `on` is `until() is not None`, `seconds_left()` the seconds until then. `/api/status` reports `auto_approve` and `auto_approve_seconds_left` (None while off or while a toggle is on), and the approvals page shows a banner with the time it turns off.

### Policy (`base/policy.py`, `eval/user_policy.yaml`)

`UserPolicy.load(path)` (or `from_dict`), `PolicyError` naming the file and field. Top-level keys `name, description, never_share, ask_first, request_topics, identifier_topics, rules, default`; `identifier_topics` (optional) maps an identifier kind (`IDENTIFIER_KINDS`) to a `never_share` topic, and egress counts a result with that identifier as having the topic (stricter only: eval/user_policy.yaml maps phone and email to parent_contact, address to home_address); rule keys `id, kinds, topics_any, topics_all, request_any, wants, pre_approved, on_ask, note`. First match wins, else `default`. `ask_first` topics must be in `never_share`; `pre_approved` only with a share form; a rule without `on_ask` answers the way its `wants` implies.

```yaml
never_share:            # topic -> keywords; guard.blocked_topics uses these
  iep: ["IEP", "504 plan", "individualized education", "special education", "speech therapy", "accommodation plan"]
ask_first: []
request_topics:         # topic -> plain description; Glimmer labels Muse's request with these
  parents: "meant for a student's family: parents, guardians, a note or letter home, a family newsletter"
  class_level: "asks for class-level numbers or patterns (an average, a count, a trend)"
rules:
  - id: class_averages
    kinds: [class_aggregate]
    request_any: ["average"]
    wants: share_summary
    pre_approved: true
    on_ask: {approve: true, remember: true}
default: {wants: ask_user, on_ask: {approve: false, remember: false}}
```

`match(item) -> Rule`, `wants(item)`, `answer(item) -> (approve, remember)`, `pre_approved(kind, topics, request="")`, `never_share -> dict`, `ask_first -> set`, `request_topics -> dict[str, str]`, `identifier_topics -> dict[str, str]`. Request topic names are lowercase words and may not repeat a never-share topic; descriptions are whitespace-collapsed. `item` is any mapping or object with `request`, `result_kind`, `topics`. For every eval item `expected == policy.wants(item)` (tested).

### Egress (`base/egress.py`)

`Egress(services, guard=None)`. `release(tool, request, raw_text, result_kind, *, job_id=None, summary=None, topics=(), item_id=None, day=None, synthetic=None) -> Released(status, text, approval_id, decision, tag_result, retryable=False)`, status `shared | waiting | refused`.
- `synthetic=None` means: True only on a cloud backend whose workspace root is marked `.synthetic`. The eval passes True.
- Tag days: every tagging step in one release (the raw result, Muse's request, a summary) uses `services.tagmap.view(tagmap.day_for(request))`: the newest tag day among the tags in Muse's request that still restore, else today. So a job, search or ask that Muse started with yesterday's tags comes back in those tags; no job column is needed, since `request` is the job's stored instructions (or the search's query and purpose). A text that is shared (release or resolve) marks its tags as sent (`TagMap.touch`), so they restore until their own day's grace window ends; the send does not extend it.
- Before tagging, the raw result (not a summary) goes through `guard.neutralize_tags`, so tag-shaped document text reaches Muse as `[Redacted N]`. If it raises, the result is held like a failed name check.
- Tagging calls `guard.tag` with `llm_names=functools.partial(answer_llm.llm_names, synthetic=...)` for every kind except `dreaming_report` (`NO_NAME_PASS`; document titles and paths get the pass). If tagging or the name pass raises, the result is held: "Held on your device.", decision refuse with floor `name_check`, audit `name_check_failed`, no decision row, and `Released.retryable` True. A summary the model could not write is held the same way (audit `summary_failed`). Muse's `request` is tagged with the roster pass (no model call) before it is routed or stored, and its identifier hits (an address, a phone) join the RouteInput's `hits`, so they floor at least `ask_user`. If tagging the request raises, the result is held like a failed topic pass (below); it is never routed on a withheld request.
- Request topics: never-share keywords found in Muse's request (`guard.blocked_topics` on the raw request, a local regex on the device whose input is never stored or sent, plus the tagged request, so "1200 Oak Avenue", tagged `[Address 1]`, still counts), plus `answer_llm.request_topics(request, policy.request_topics)` on the tagged request for every kind except `document_list` and `dreaming_report` (`NO_TOPIC_PASS`). The model pass is also skipped when the result's own never-share topics already make the floor refuse (`router.never_share_floor`), since its labels could not change the outcome. Both join `topics` and the result's own keyword topics in the RouteInput and the decision row. The result's own topics also get `identifier_topics(tagged.hits, policy)`: the policy's `identifier_topics` for the result's own identifier hits (not the request's: an address only in Muse's request still asks), so a contact snippet with a phone number is refused (floor `blocked:parent_contact`) instead of asked about. A never-share topic found only in the request (not in the result or the passed `topics`) also goes in `request_blocked`: an `ask_user` floor `request:<topic>`, so "Which students have an IEP?" over a list of tags asks the user even though the answer has no keyword, and the floor never refuses "Do not mention any IEP" by itself (the router model, a policy refuse rule or a learned refuse rule still can). Module helpers, also used by `scripts/cloud/quant_eval_modal.py` so its lookups match: `request_keyword_topics(raw_request, tagged_request, never_share, scan=None)`, `needs_topic_pass(result_kind, tagged, own_topics, policy) -> bool` and `route_input(asked, result_kind, tagged, own_topics, asked_about, never_share, summary=None) -> RouteInput` (hits are the result's plus the tagged request's identifier hits; topics are `own_topics` then `asked_about`). If the model pass raises, the result is held like a failed name check: floor `topic_check`, audit `topic_check_failed`, no decision row, `retryable` True. The row's `shown_form` is `default_share_form(kind, topics)`.
- Then route, record one decision row (with `blocked`), and return. `share_summary` (and `ask_user` whose shown form is a summary: `class_aggregate`, or a `class_level` request) shares the tagged `summary`, or one the answer model writes from the tagged text; a summary that still has a `[Student X]` or `[Person N]` tag, or a sentence that describes one student (`router.singles_out`), is refused; with `DEVICE_ONLY=1` those sentences are dropped and only a summary with no sentence left is refused.
- `resolve(approval_id: int) -> Released`: pending -> waiting, approved -> the stored tagged text, denied or deleted -> "Kept on your device.". `approval_id` is set for waiting rows and resolve results only.
- Texts to Muse: "Waiting for your OK on the device.", "Kept on your device. <one fixed sentence for the floor that kept it>" (`refusal_text(floors)`; the router's own reason is model text and stays on the approval page), "Held on your device.". After a shared result egress emits `sending`, then `waiting` or `idle`. Every one passes `final_check(text) -> list[Hit]` (`guard.leaks`; fails closed).

### Services (`base/services.py`)

`Services.create(settings, *, light=True, heavy=None)` wires one of each (with `owner=True` it also drops expired tags once, `retention.maybe_expire_tags`): `settings, events (base.events), roster (guard.load_roster), tagmap (TagMap.for_settings), policy, answer_llm, router_llm (LocalLLM roles), router, approvals, jobs, index, heavy (HeavyQueue on paths.db with wait_seconds=HEAVY_WAIT_SECONDS=120 when settings.heavy_queue, else None), agent (with heavy), audit (connector.audit.Audit on paths.db), egress, night (NightRunner), light (start_light)`. `Services.create(..., owner=True)` also fails jobs a stopped process left unfinished, tells `events` how many approvals are pending and settles them (`events.settle("startup")`, before the light starts), so a restart with cards waiting shows waiting on the light and the page instead of idle, and on llama_server with `DREAMING_BACKEND=lora` finds the router adapter's id (`GET /lora-adapters`, the entry ending in router.gguf) for `Router(adapter=...)`. `Services.for_eval(settings)` is the same with no light, no heavy queue, `owner=False` and a `QuietEvents` bus, so a night never drives the light or the page; `eval/run_eval.py` and the dreaming gate use it. `close()` stops the agent's model steps and the light and closes the store and model clients. Modules that need others take a `services` object; tests pass a `types.SimpleNamespace` with only what they use.

`python -m base` (or `python -m base.server`) builds Services, the approval page and the connector, and runs both uvicorn servers in one loop until Ctrl+C or SIGTERM, then closes Services. httpx request logging is turned down so no model or worker URL is logged.

## Connector (`base/connector/`)

- `server.py`: `connector_app(services, *, token=None)` is the MCP server (official `mcp` SDK, streamable HTTP, stateless, JSON responses) at `/mcp` plus `GET /health` without auth, served on 127.0.0.1:8790. Every other path needs `Authorization: Bearer <token>` from `settings.paths.connector_token` (made 0600 on first use). The SDK only accepts Host headers 127.0.0.1 or localhost. A standalone GET stream gets 405.
- Tools and annotations (Muse classes tools Read, Write, Sensitive write):

| Tool | Muse class | Input | Returns |
|---|---|---|---|
| list_documents | Read | folder | tagged titles and relative paths, through egress, as plain text when shared or refused. A title or path with a never-share keyword is left out and counted: "N documents held back on the device." Released as a finished job of kind `list` like a search, so a list that waits for the user's OK (a title with a name the roster does not know) is `{job_id, status: "waiting", result, retry_after_seconds, next}` and a retried identical list joins that release |
| search_documents | Read | query (tags restored locally), purpose (optional, never searched) | up to 5 snippets of 300 characters, through egress. - Saying what a result is for: INSTRUCTIONS and the run_private_task and search_documents descriptions ask Muse to say who a result is for and what it will be used for ("for my own grading", "for the family newsletter", "to send to the principal"), in run_private_task's instructions and in search_documents' `purpose`, so egress's request topics have something to read.
- Release tools: `RELEASE_TOOLS` maps a job kind to the tool its decision rows name: `search` search_documents, `ask` ask_device, `list` list_documents, `save` save_on_device, anything else get_result. Kinds `search`, `ask` and `list` never get `SAVED_NOTE` (`NO_SAVED_NOTE`).
- Search releases: the request egress sees is the query, or `"<query>\nPurpose: <purpose>"` when a purpose is given (tagged and labeled like any request; only the query is searched). The snippets become a finished job, `jobs.job_for_result("search", request, raw, "snippet") -> job_id` (kind `search`, status `done` at once, so it never counts toward MAX_ACTIVE_JOBS; the raw snippets stay in `raw_result` on the device), and are released by the same claim, thread and `RELEASE_WAIT_SECONDS` wait as get_result, with tool `search_documents` on the decision row (`RELEASE_TOOLS`). Past the wait the answer is `{job_id, status: "running", result: SEARCH_CHECKING_NOTE}` (audit `pending`); a waiting release is `{job_id, status: "waiting", result}`; Muse follows either with get_result. While a job with the same kind, request and raw result is unreleased, releasing or waiting, `job_for_result` returns it, so a retried search joins that release and never makes a second release or approval card; once it is shared or refused, the same search later is a new job with its own check.
- Tags from Muse: `check_tags(services, *texts)` raises `ToolFailure(EXPIRED_TAG, outcome="expired_tag")` when `tagmap.expired(t)` lists anything for one of the texts or `tagmap.mixed_days(*texts)` is True: "That tag no longer works on this device. Call list_documents or search_documents again for current tags." `restore_tags(services, text)` calls it, then restores with `tagmap.for_muse()` (with a TagMap; a plain dict as before). search_documents and ask_device check the whole request (the query or question plus `Purpose:`, whose tags pick the result's tag day) and then restore the query or question; run_private_task (instructions, before the folder is looked up) and list_documents (folder) restore theirs; save_on_device checks every item's for_tag, title and body together, each read on its own (a title ending in "student" and a body starting with "I" are not "Student I"); so nothing is searched, listed, started or saved. Expired, never-sent and guessed tags and a request that mixes two tag days get the same sentence, so no answer puts a person from an older day's tags into today's tags. With `TAG_ROTATION=off` nothing is refused and every known tag restores, as before.
- Result shapes for multi-step use: every queued, running or waiting answer carries `retry_after_seconds` (20) and `next` ("Call get_result with this job_id and wait_seconds 25."). Every refused answer (plain text or `result`) ends with `REFUSED_END`, "Do not look for this another way. The user can open it on the device.", added once after egress's text. A waiting or refused private task whose `output/<job id>/` holds files also gets `SAVED_NOTE`, "The full result is saved on the device in output/<job id>.", before it; it names only the job id, never a file name, and search and ask jobs never get it. A shared text is sent exactly as egress released it, so it matches the receipt's `sha256`; the added sentences are fixed text and the job id, and the receipt hash covers egress's text without them. A missing or unknown job id says "Pass the job_id that a Muse Privacy tool returned." INSTRUCTIONS say once that tags change daily and an older tag stops working about a day and a half after its day ends, however often it is used (TAG_GRACE_HOURS, so use the tags from the current results and keep to one day's tags in a request), that get_result can wait with `wait_seconds`, and that a scheduled job calls only the tool it names, once. `USAGE` has a sentence for every tool that takes arguments.
- Waiting and the call budget: `Connector.call` starts one `CALL_BUDGET_SECONDS` (45) budget per tool call (`Connector(services, clock=time.monotonic, wait=Event.wait)`; tests pass fakes). The first-release wait in search_documents (after retrieval and passage picking) and get_result is `min(RELEASE_WAIT_SECONDS, max(MIN_WAIT_SECONDS, what is left))`, so a call answers before the relay client's 55 s and the relay's 60 s. With `wait_seconds`, get_result keeps looking until `min(now + wait_seconds, the budget's end)`: a waiting release blocks on `approvals.wait_decided` (the answer returns the moment the user taps Share it or Keep it here), and a queued or running job, a release another call is checking, or a running night is looked at again every `POLL_SECONDS` (0.5). At most `MAX_WAITERS` (8) calls wait at once; past that a call answers at once.
- Failures reach Muse as one plain sentence. Audit outcomes: `shared, waiting, refused, started, done, pending, failed, bad_input, busy, error, cloud_refused, expired_tag`; egress adds `egress_blocked`, `name_check_failed`, `topic_check_failed`, `summary_failed`, `auto_approved` and `auto_approve_skipped`. Tool `initialize` records the MCP client's name as the outcome (`client_label`: lowercase letters, digits and `_`, starting with a letter, at most 40, "client" when there is none), from initialize's `clientInfo.name` only.
- `audit.py`: `audit(db, tool, outcome, ms=0, via=None)`, `recent(db, limit=50)`, `Audit(db)` callable as `services.audit(tool, outcome, ms=0, via=None)`, table `audit(ts, tool, outcome, ms, via)`; `via` is `relay` or `local`, and None means the call in progress (`CURRENT_VIA`, a context variable, `local` outside a call). The connector's middleware sets `CURRENT_VIA` from the `x-muse-privacy-via` header (`VIA_HEADER`; only the exact value `relay` counts) for each MCP message, and release threads run in a copy of the context, so egress's rows during a relayed call say `relay` too. An older table gains `via TEXT NOT NULL DEFAULT 'local'` on first open. Labels must be short lowercase words; never content.
- `relay_client.py`: dials out to `RELAY_URL` over WebSocket with the device secret, forwards each JSON-RPC message to the local MCP server with the device token and `x-muse-privacy-via: relay`, returns responses. Reconnects with backoff. `python -m base.connector.relay_client pair` asks the relay for an 8 character one-time pairing code (single use, 10 minute expiry) and prints it; `unlink` revokes every Muse link. A cleartext RELAY_URL is refused unless it is loopback. `RELAY_PROXY` (`Settings.relay_proxy`, `proxy_mode(settings)`): `system`, the default, dials the relay socket through the system or environment proxy (websockets' `proxy=True`) and builds the register, pair and unlink clients with `trust_env=True`; `direct` passes `proxy=None` and `trust_env=False`, for a proxy the relay refuses (Cloudflare error 1010). The local forward to 127.0.0.1 never uses a proxy. `run` exits 3 (the unit's RestartPreventExitStatus) when the secret is rejected (HTTP 401, `RelayAuthError`) or another copy took over. The relay answers 401 for a bad secret and never 403, so a 403 (Cloudflare's edge or a proxy) is a refused connection: `run` logs it with `PROXY_HINT` (try RELAY_PROXY=direct) and keeps backing off, and register, pair and unlink raise a plain `RelayError` that says the same.

## Relay (`relay/`, Cloudflare Worker, TypeScript)

- Worker + one Durable Object per device. Device endpoint `GET /device/connect` (WebSocket, `Authorization: Bearer <device secret>`), `POST /device/register` (returns device id + secret once), `POST /device/pair` (device asks for a pairing code). `POST /device/unlink` (bearer secret) revokes every OAuth grant bound to the device and returns `{"revoked": n}`. Muse endpoint `POST /mcp` (streamable HTTP, OAuth bearer), OAuth via `@cloudflare/workers-oauth-provider` with dynamic client registration; the authorize page asks for the pairing code, which binds the grant to that device. The relay stores no tool content; it forwards bytes and keeps only device ids, hashed secrets and grants.
- Read-only links (Nov 3, Muse Connector Platform guideline 3.1): the authorize page offers Full access (default) or Read only, kept across a mistyped code; the grant's props are `{deviceId, readOnly}` and grants from before have no `readOnly` (full access). On a read-only grant, `relay/src/readonly.ts` answers any `tools/call` whose tool is not in `READ_TOOLS` (list_documents, search_documents, ask_device, get_result, dreaming_report; an allowlist, so a new device tool is blocked there until added) with a readable `isError` result and never forwards it; a batch holding one is answered whole without forwarding. A `tools/list` answer is filtered to `READ_TOOLS` (JSON or each event-stream `data:` line; an unparseable body becomes an empty list).
- Review codes: `POST /device/pair` with `{"review": true}` issues a code good for `REVIEW_USES` (20) links within `REVIEW_TTL_SECONDS` (14 days), answered as `{code, expires_in, uses}`; any other body gives a one-time 10 minute code with `uses: 1`. The `codes` table has `uses_left` (added with `ALTER TABLE` on an older table); redeeming decrements it and deletes the code at the last use. A newer code for the device still replaces it. `relay_client pair --review` asks for one.
- Modal relay (`relay_modal/`, Python, Nov 3): the same endpoints, frames, read-only rules, review codes and readable results, served by one always-on Modal container (`modal_app.py`: `min_containers=1`, `max_containers=1`) that holds every device socket in memory (`hub.py`) and one SQLite file on a Modal Volume, committed after each write (`store.py`). It is its own OAuth 2.1 server (`app.py`): PKCE S256 only, dynamic client registration (public or client-secret), Client ID Metadata Documents (https client_id fetched only from public addresses, 64 KB, no redirects, cached 1 h; treated as public clients), loopback redirects on any port (RFC 8252), `iss` on every redirect, `resource` must be the /mcp URL or the origin, access tokens 1 h, refresh tokens 30 days rotated on use (the replaced one works 60 s more), revocation on the token endpoint. Secrets, codes, IPs and tokens are kept only as hashes or HMACs. `RELAY_ORIGIN` pins the public origin. Tests: `tests/test_relay_modal.py`.

## Dreaming (`base/dreaming/`)

- `dataset.py`: `build(store, synthetic_path, holdout_ids=()) -> list[Example(request, result_kind, tagged_text, label, weight, topics, source, approved, remember, row_id, item_id)]`. User rows weigh 3, synthetic rows 1. Skips deleted rows and holdout ids. Labels come from `approvals.label_for`.
- `train.py`: `train(examples, settings, backend=None, *, out_path=None, day=None, policy=None) -> TrainResult(backend, path, rules, examples, user_examples, cloud_required, message)`. Backend `prompt` (default) groups examples by `rule_key(kind, topics, relevant_topics(policy))` (relevant topics: never-share topics, request topics and every rule's topics) and writes one rule line per group with exact counts, plus strict topic rules `(topic: X)` that need evidence of their own, from scratch each night (deterministic, no model call). A group with a never-share topic the floor refuses (`floored_topics`) gets no practice rule, and only an ask first or refuse rule from the user's own decisions: a result with such a topic in its own text is refused without a card, so the user only answers when Muse's request alone names it (floor `request:<topic>`), and a learned refuse rule then lifts that ask to `learned:refuse`; a share rule there would change nothing, so none is written. Share rules need more (Oct 30, HANDOFF open item 12, the t085 case): a share rule for a whole kind (`topics: none`) needs `MIN_KIND_SHARE_DECISIONS` (5) decisions that all agree, and a group with a destination topic (`destination_topics(policy)`: request topics a policy ask_user or refuse rule names, so parents, third_party, full_text and deanonymize in eval/user_policy.yaml; `DESTINATION_TOPICS` with no policy) never gets one, from your decisions or practice data; ask first and refuse rules keep `MIN_DECISIONS` (2) at `MIN_AGREEMENT` (0.8). The header says so: such a topic in a result's own text is always refused, one named only in Muse's request is asked about unless a refuse rule holds. `read_rules(text) -> list[RuleLine(kind, topics, decision, source, text)]`, `match_rule(rules, kind, topics)` (the one rule shown: your exact group, else your strictest topic rule, else the same from the practice defaults) and `learned_floor(rules, kind, topics) -> RuleLine | None` (the strictest ask first or refuse rule among the match and every rule that `covers(rule, kind, topics)` the result: same kind with a subset of its topics, or a topic rule for one of them; your rules first, practice defaults only when none of yours covers it) read them back for the router. The file's header says the same: the best-fitting rule is shown, and an ask first or refuse rule also holds for every result of its kind that has all of its topics, with or without more. Backend `lora` writes `adapters/train-<date>.jsonl` and says to run `scripts/cloud/train_lora_modal.py`; it never launches it. In that file a row the user did not approve has its request and text withheld, and a row in which `guard.leaks` (roster and tag map) still finds anything is left out; with no roster or tag map nothing is written.
- `gate.py`: `gate(services, candidate_rules_path, current_rules_path, holdout_items, *, force=False) -> GateResult(keep, before, after, reasons, rerun)`. Paired, so run-to-run flips on a few items cannot reject a good night: the current rules are scored once with `run_eval.evaluate` on the holdout in a fresh temp home; `changed_items` then compares `services.router.learned_view(inp, rules_text)` under the current text (`""` when there is no current file) and the candidate text for each item's RouteInput from that run, and the candidate is run, in another fresh home, only on the items whose view differs, plus any item the current run could not route (it raised, or a check held it before the router: no RouteInput). Every other item reuses the current run's row (`reused: true` in the gate's raw rows), and `paired` merges them with `run_eval.rescore` into `after` (`name` gate-candidate). `rerun` is the number of items re-run. Services with no router that has `learned_view` re-run every item. This assumes a rule that is neither shown with an item nor behind its learned floor does not change that item's decision (the system prompt lists every rule, but step 3 makes only the shown ones binding, and the floor is in code). Keep only if overall accuracy, every category and agreement are no worse, leaks are 0 (a leak on a reused item counts against the candidate too), and missed asks and refusals shared (`EvalReport.missed_asks`, `refuse_shared`) are no higher than the current rules' (a refused item shared tagged is not a leak, so these are checked on their own), and neither side has more than 10% of items that errored or fell back (`MAX_UNSCORED_SHARE`), so a night scored while the model was down keeps the current rules. `force` replaces rules learned from since-deleted decisions as long as the candidate leaks nothing. `controls_path` (a privacy_controls.json, set by the simulation through `NightRunner.controls_path`) is copied into every home the gate scores in, so a persona's toggles hold on the holdout too.
- `night.py`: `NightRunner(services, *, holdout_path=None, synthetic_path=None)`: `start() -> job id` (the running one if a night is going), `run_night() -> NightReport` (raises `DreamingBusy(job_id)`), `running_job()`, `wait(timeout)`, `last_report() -> dict` with `learned_from, accuracy_before, accuracy_after, agreement_before, agreement_after, kept, leaks, seconds, night_number` (night 0, learned_from 0 and None for the rest before the first night). Lock and history in tables `dreaming_lock` (with an `owner` of pid and a per-process token: a lock whose process is gone is not a running night) and `dreaming_nights`. `report_for(job_id)` gives one night's numbers, and `last_finished_at() -> (job_id, finished_at) | None` the latest finished night (the connector's once-a-night check). `NightReport.approval_requests` counts decision rows with router `ask_user` (not deleted) from when the previous night finished, at most 24 h back (`ASK_WINDOW_SECONDS`), to the night's start, and `still_asked` how many of them the rules in place after the night would still ask: each row is rebuilt as a RouteInput (`replay_input`: tagged request and text, topics, blocked, and from the receipt's floors the identifier kinds and request-only topics; a `compliance:` floor counts as still asked) and decided in code by `_RulesOnly` (the Router with `mode()` fixed to rules, no model call). Both are in `REPORT_KEYS`, so `last_report()` and `report_for` carry them (None in nights from before them, and `still_asked` None when the services have no policy). `NightReport.categories` holds holdout accuracy per expected decision; `NightReport.missed_asks` and `refuse_shared` are the holdout's for the rules in place; `NightReport.gate_rerun` is the gate's `rerun` (None when the gate did not run), and the note says "The gate re-ran N of M holdout items on the new rules". Neither is in `last_report()`. `synthetic_path=""` means no practice data; `raw_dir` (set by the simulation) gets each night's gate rows; `exclude_ids` (set by the simulation: its unseen test items) are left out of the dataset like the holdout ids, so practice data that contains them never teaches them. `controls_path` (set by the simulation: a persona's toggles) goes to the gate and to the score of the current rules; None means the defaults.

## Starting and staying up (`scripts/start.sh`, `scripts/supervise.sh`)

- `routes.py`: `make_router(queue, token)`, `router_for(settings, queue=None)`, `load_token`, `print_token` (`python -m base.heavy.routes` prints the worker token). `TokenGate` checks the bearer token for every /heavy/ path before any body is read; the approval app's `BodyLimit` answers 413 above 64 KB (2 MB for /heavy/<id>/result). `python -m base.heavy.routes rotate` replaces the token. `POST /heavy/hello {worker, cloud}`, `GET /heavy/next?worker&cloud&wait` -> `{id, kind, messages, schema, synthetic}` or 204, `POST /heavy/{id}/result {result} | {error}` -> 200, 409 if abandoned, 404 for a bad id; 401 for a bad token. The approval page includes these routes when `settings.heavy_queue` is on.
- `worker.py` on the laptop: `python -m base.heavy.worker --jetson-url URL --token TOKEN [--synthetic] [--ca-cert PEM] [--allow-plain-http]` dials out to the Jetson and runs each step on the laptop's Glimmer. A non-loopback http URL is refused unless `--allow-plain-http`; with `--ca-cert` the Jetson's self-signed certificate is the only one trusted. Each step's model timeout stays 10 s under the `wait_seconds` that /heavy/hello returns. A worker counts as present while it holds a step claimed within wait_seconds, and a submitted result counts as a hello.

## Cross-module details pinned on Oct 27

### Jobs and releases
The connector's `get_result` (and `search_documents`, through a `jobs.job_for_result` job of kind `search`) first claims the release (`jobs.claim_release`); a call that loses the claim, or finds release status `releasing`, answers `{status: "running"}` with "The device is still checking this result.". The winner runs the release on a thread and waits up to `RELEASE_WAIT_SECONDS` (40), or less when less of the call's 45 s budget is left (at least 1 s), under the relay client's 55; past that it answers `running` and the release finishes in the background. A retryable release resets the claim and answers `running`, up to `MAX_CHECK_FAILURES` (3) in a row, after which it is stored as refused. The release itself calls `egress.release(RELEASE_TOOLS.get(job.kind, "get_result"), job.instructions, job.raw_result, job.result_kind, job_id=..., summary=job.summary, topics=job.topics)` (tool `search_documents` for kind `search`, so a search's decision row names the search) the first time a finished job is read and stores the outcome with `jobs.set_release(job_id, status, approval_id=int | None, released_text=...)`. While the release status is `waiting` it calls `egress.resolve(int(approval_id))` and stores the outcome once it changes. Shared and refused releases are resent from `released_text`. The approval page decides rows through `ApprovalStore.decide`; nothing is pushed to Muse.

With tag rotation, the release tags on the tag day of the newest restorable tag in `job.instructions` (Egress, tag days), so a job whose instructions carry yesterday's tags, or that started before midnight and finishes after it, answers in the tags Muse used. A job whose instructions have no tags is tagged on the day it is released. A resend from `released_text` does not mark tags as sent again.

### Heavy-step hook
The workspace agent takes an optional `heavy` object with `run(kind, messages, schema, *, synthetic=False) -> dict | None`. `None` means no laptop worker is available and the step runs on the device's own Glimmer; an exception does the same. The agent passes `synthetic=True` only for folders marked `.synthetic`. Services builds one `HeavyQueue` and shares it between the agent and the `/heavy` routes.

### Relay frames (relay/ and base/connector/relay_client.py must agree)
The device opens `wss://<relay>/device/connect` with `Authorization: Bearer <device secret>`. Frames are JSON text messages.
- Relay to device: `{"type": "request", "id": "<uuid>", "method": "POST" | "GET" | "DELETE", "headers": {"content-type": ..., "accept": ..., "mcp-session-id": ..., "mcp-protocol-version": ...}, "body": "<raw request body text>"}`
- Device to relay: `{"type": "response", "id": "<same uuid>", "status": 200, "headers": {"content-type": ..., "mcp-session-id": ...}, "body": "<raw response body text>"}`. If the local server answers with `text/event-stream`, the device collects the SSE `data:` lines for that request and sends them as one body with content-type `text/event-stream` (no long-lived streams in v1).
- Keepalive: either side may send `{"type": "ping"}`; the other answers `{"type": "pong"}`.
- Registration: `POST /device/register` with JSON `{"name": "<device label>"}` returns `{"device_id": "...", "secret": "..."}` once; the relay keeps only a SHA-256 of the secret. `POST /device/pair` with the bearer secret returns `{"code": "ABCD2345", "expires_in": 600}`, eight characters from an alphabet without 0/O/1/I, single use.
- The relay answers `503 {"error": "device offline"}` when no device socket is connected, and `504` after 60 seconds with no response frame.
- Readable tool results (`relay/src/toolresult.ts`): when the forward fails with 503 or 502 (offline, or the device's app is not running), 504 (too slow) or 429 (busy) and the POST body is one JSON-RPC object with `method` `tools/call` and a string or number `id`, the relay answers `200 application/json` `{"jsonrpc": "2.0", "id": <same>, "result": {"content": [{"type": "text", "text": <a fixed sentence>}], "isError": true}}` (`OFFLINE_TEXT`, `TIMEOUT_TEXT`, `BUSY_TEXT`). initialize, tools/list, notifications and batches keep the status codes. The body is parsed only then, only for method and id, and never stored or logged.

### No network off the device (tests)
`tests/conftest.py` has the `loopback_only` fixture: `socket.socket.connect` and `connect_ex` to anything but 127.0.0.1, ::1, localhost or a Unix socket raise AssertionError, and `socket.getaddrinfo` for any other host fails the test; it yields the list of attempts (`connect <host>`, `lookup <host>`), so a test also fails when the code under test caught the error. `tests/test_no_egress.py` (COMPLIANCE_PLAN 1.4) runs real Services with `DEVICE_ONLY=1` and `SEARCH_EMBEDDINGS=1` over copies of the invented demo files, serves LFM3-VL-2B (127.0.0.1:8083) and EmbeddingGemma (127.0.0.1:8084) in process with respx, records and refuses every other HTTP request, and drives all seven tools through the in-process MCP client (list_documents, search_documents including a scanned form and a tag Muse was given, ask_device and run_private_task with get_result, run_dreaming, dreaming_report). No tool output may hold a roster name, nickname or student id from eval/roster.json or a `guard.leaks` hit. With LFM3-VL-2B down (HTTP 503) listings and searches are held ("Held on your device.") and ask and task jobs fail with "nothing was shared"; with the embedder down search uses keywords only.

Pairing codes: wrong codes are counted in `BASE_HOME/pairing_misses` across restarts; after 10 the server stops printing a code at start and only `POST /api/pair-code` from the device itself issues one (and clears the count). `POST /api/sessions/clear` signs out every other browser.
